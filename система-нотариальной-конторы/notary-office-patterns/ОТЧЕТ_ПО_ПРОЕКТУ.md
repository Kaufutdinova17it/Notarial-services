# Паттерны проектирования в микросервисной системе нотариальной конторы

Проект разделён в соответствии с исправленным архитектурным планом на ClientService,
ServiceCatalogService, ApplicationService (включая документы), PaymentService и
NotificationService. Внешним входом является API Gateway. Каждый доменный сервис
имеет собственную базу PostgreSQL на общем сервере; чужие данные запрашиваются через HTTP API.

## Порождающие паттерны

### 1. Builder (Строитель)

Пошагово создаёт заявку: добавляет клиента, выбранную услугу, описание и исходные
документы. Перед созданием проверяет обязательные поля и устанавливает статус
«Создана». Клиент и услуга предварительно получены ApplicationService через API
соответствующих сервисов.

**Модуль:** `application-service`.  
**Класс:** `ApplicationBuilder`.

```java
Application application = new ApplicationBuilder()
        .forClient(client)
        .withService(service)
        .withNote(note)
        .attachSourceDocument("passport.pdf")
        .build();
```

### 2. Factory Method (Фабричный метод)

Создаёт уведомления разных типов в зависимости от HTTP-события: создание заявки,
изменение статуса, готовность документов, отклонение или отмена. Каждая фабрика
формирует свой текст сообщения.

**Модуль:** `notification-service`.  
**Классы:** `NotificationFactory` и конкретные фабрики уведомлений.

```java
Notification notification = NotificationFactory
        .forEvent(eventType)
        .createNotification(application, client);
```

### 3. Singleton (Одиночка)

Обеспечивает одно соединение с собственной базой внутри каждого микросервиса.
Экземпляры различаются по имени базы, поэтому ClientService и PaymentService не
разделяют ни соединение, ни таблицы.

**Модуль:** `common`.  
**Класс:** `Database`.

```java
Database database = Database.getInstance("clientdb", clientSchema);
```

## Структурные паттерны

### 4. Adapter (Адаптер)

Согласует интерфейс платёжного сервиса приложения с внешней платёжной заглушкой.
Преобразует сумму из рублей в копейки, а числовой код ответа — в объект результата
платежа.

**Модуль:** `payment-service`.  
**Классы:** `PaymentGateway`, `PaymentStubAdapter`, `ExternalPaymentStub`.

```java
@Override
public PaymentResult pay(Long applicationId, BigDecimal amountRubles) {
    long amountKopecks = amountRubles.movePointRight(2).longValueExact();
    int code = externalPaymentStub.makePayment(
            amountKopecks, "APP-" + applicationId);
    if (code == ExternalPaymentStub.CODE_SUCCESS) {
        return PaymentResult.success(externalPaymentStub.lastTransactionId());
    }
    return PaymentResult.failure(externalPaymentStub.describeCode(code));
}
```

### 5. Decorator (Декоратор)

Расширяет отправку уведомлений журналированием и повторными попытками без изменения
основного отправителя.

**Модуль:** `notification-service`.  
**Классы:** `EmailNotificationSender`, `LoggingNotificationSender`,
`RetryNotificationSender`.

```java
NotificationSender sender = new RetryNotificationSender(
        new LoggingNotificationSender(emailSender), 3);
```

### 6. Facade (Фасад)

API Gateway предоставляет браузеру единый интерфейс и скрывает координацию пяти
удалённых сервисов. Например, при ответе с подробностями заявки Gateway объединяет
данные ApplicationService и PaymentService, а имя клиента и название услуги получает
из их API. Прямых вызовов доменных Java-сервисов и обращений к их базам нет.

**Модуль:** `api-gateway`.  
**Класс:** `NotaryWebServer`.

```java
Map<String, Object> result = applicationView(Models.toMap(application));
result.put("documents", applicationService.get(
        "/api/applications/" + applicationId + "/documents"));
result.put("payments", paymentService.get(
        "/api/payment/application/" + applicationId));
```

## Поведенческие паттерны

### 7. Observer (Наблюдатель)

ApplicationService публикует событие после создания заявки или изменения её статуса.
`AuditLogListener` записывает событие в собственную базу ApplicationService, а
`RemoteNotificationListener` передаёт его по HTTP в NotificationService. Недоступность
сервиса уведомлений протоколируется и не откатывает уже выполненную смену статуса.

**Модуль:** `application-service`.  
**Классы:** `ApplicationEventPublisher`, `ApplicationListener`, `AuditLogListener`,
`RemoteNotificationListener`.

```java
eventPublisher.publish(new ApplicationEvent(
        ApplicationEventType.APPLICATION_CREATED,
        application.getId(), application.getClientId(),
        "заявка создана"));
```

Точка приёма события в NotificationService:

```text
POST /api/events/applications
```

### 8. State (Состояние)

Управляет жизненным циклом заявки и проверяет допустимость изменения статуса.
Например, заявка может перейти из «Создана» в «В процессе», а завершённая заявка не
может снова вернуться в обработку.

**Модуль:** `application-service`.  
**Классы:** `ApplicationStateMachine`, `CreatedState`, `InProgressState`, `ReadyState`,
`TerminalState`.

```java
public ApplicationStatus transitionTo(ApplicationStatus target) {
    currentState.ensureTransitionAllowed(target);
    currentState = stateOf(target);
    return target;
}
```

### 9. Strategy (Стратегия)

Выбирает алгоритм расчёта стоимости услуги: фиксированный тариф, процент от суммы
сделки или льготный тариф со скидкой. PaymentService получает заявку и услугу через
HTTP API, а не через репозитории других модулей.

**Модуль:** `payment-service`.  
**Классы:** `PricingStrategy`, `FixedPricingStrategy`, `PercentagePricingStrategy`,
`PrivilegedDiscountStrategy`.

```java
PricingStrategy strategy = PricingStrategy.forPricingType(
        service.getPricingType());
BigDecimal amount = strategy.calculate(service, context);
```
